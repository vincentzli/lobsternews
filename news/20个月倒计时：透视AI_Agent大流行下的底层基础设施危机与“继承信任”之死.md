# **20个月倒计时：透视AI Agent大流行下的底层基础设施危机与“继承信任”之死**

在加利福尼亚州门洛帕克 Nia 酒店举行的 VB Transform 2026 大会上，Meta 工程副总裁巴拉克·亚古尔（Barak Yagour）戴着 Ray-Ban Meta 智能眼镜登台，向整个企业 IT 与科技界发出了震聋发聩的警告：在传统遗留基础设施被自主 AI Agent 的重载彻底压垮之前，企业只有大约 20 个月的时间来对底层系统进行彻底的重构。

亚古尔指出，在仅仅六个月的时间里，Meta 数据系统承载的由自主 AI Agent 触发的查询请求量就暴增了 3000%（整整 30 倍）。这绝非渐进式的演进，而是一场颠覆性的技术海啸，它直接摧毁了现代系统设计的三个底层基石：**并发容量（Capacity）、身份鉴权（Identity）与系统流速（Velocity）**。

“现有的企业系统是为人类用户设计的，而不是为自主 Agent 准备的，”亚古尔直言不讳，“它们根本无法支撑大规模自主 AI Agent 的并发运行。”随着人类的角色从“置身流程之中（working in the loop）”转向“凌驾于流程之上（operating over it）”进行调度，底层的数据库、IAM 协议和数据管道必须迎来一次脱胎换骨的结构性变革。

#### 30倍查询风暴：被撞碎的并发红墙
传统的企业系统容量规划，完全是围绕人类用户的交易足迹展开的。一个人登录系统，执行几次数据库查询，浏览一个页面，然后登出。即便是最活跃的“重度”人类用户，其产生的数据流量也极低，且具备高度的可预测性。

相比之下，自主 Agent 则在无休止的闭环中运行。LangChain 首席执行官哈里森·切斯（Harrison Chase）曾指出：*“AI Agent 的可靠性上限，完全取决于其背后的数据基础设施。”* 当 Agent 被赋予开放式目标（如“优化这条供应链”或“审计我们完整的客户注册表”）时，危机就爆发了。在系统底层，这些 Agent 会执行复杂的推理链，并分裂出多个子 Agent。

这种递归调用直接导致了经典的**“查询风暴（Query Storm）”**。在标准的传统关系型数据库（如 PostgreSQL 或 MySQL）中，这种高频、机器节奏的查询负载会瞬间引发以下问题：
1. **连接池枯竭（Connection Pool Exhaustion）**：AI Agent 瞬间启动数百个并发子任务，会刹那间耗尽数据库连接池（例如 PgBouncer），导致数据库延迟呈指数级飙升。
2. **锁竞争（Lock Contention）**：当关系型引擎试图处理来自多个并行 Agent 循环的并发写入操作时，会撞上严重的锁竞争红墙，系统吞吐量雪崩式下滑。
3. **WAL（预写日志）瓶颈**：Agent 级更新的高速和超高频直接打爆了预写日志（Write-Ahead Logging），导致磁盘 I/O 出现严重的物理瓶颈。

为了缓解这一状况，企业正被迫向能够水平扩展的分布式 SQL 架构（如 CockroachDB 或 TiDB）转型，同时引入资源感知的限流机制和熔断器。与以往基于请求频率保护服务器不同，现代熔断器一旦检测到重复的、循环的查询行为或不断攀升的延迟，就会瞬间强行终止 Agent 的执行循环。

#### Meta 数据管道变革：从批处理走向推理驱动的实时流
为了与 35 亿人类用户并列，将数百万自主 Agent 作为一等基础设施消费者进行支撑，Meta 正在大刀阔斧地重构其推荐引擎与数据管道。

历史上，推荐系统极度依赖批处理和离线推理——即定期计算用户偏好，并通过快速的模式匹配检索来提供服务。然而，AI Agent 要求的却是实时的状态同步。如果一个 Agent 修改了数据库，其推理循环的下一步必须能够瞬间感知并反映出这一状态变化。

Meta 正在将其数据层从批处理管道彻底转向实时流处理，将计算范式从简单的模式匹配升级为主动推理。这使得推荐引擎能够将富含上下文的实时嵌入（Embeddings）直接输送至 Agent 的上下文窗口中，从而避免 Agent 因获取过期信息而做出错误决策。

#### 身份危机：“继承信任”与 Moltbook 灾难性泄露
在 Agent 时代，或许最危险的安全漏洞莫过于**“继承信任（Inherited Trust）”**这一安全模型。在以人类为中心的企业中，身份与访问管理（IAM）系统通过 SSO、MFA 或硬件令牌验证人类凭证。然而，当人类部署一个自主 Agent 去执行任务时，该 Agent 通常会直接继承创建者所拥有的全部权限、凭证和 API 访问权。

这种过度授信（Over-scoping）无疑是一颗定时炸弹。Token Security 联合创始人兼 CEO 伊塔马尔·阿佩尔布拉特（Itamar Apelblat）最近在《福布斯》上尖锐地指出：
> “仅仅因为‘继承信任’关系赋予了某些权限，AI Agent 决不能因此演变成一个能够随意修改云基础设施的身份实体。”

当一个 Agent 继承了宽泛且长效的凭证时，一次简单的提示词注入攻击（Prompt Injection）或被投毒的数据库上下文，就能瞬间劫持该 Agent 的推理引擎。随后，Agent 会使用合法继承的人类凭证登录系统并执行恶意操作，这直接让传统的特征码检测手段失效。

忽视 Agent 身份安全所带来的灾难性后果，已在 2026 年 2 月初爆发的 **Moltbook 安全事件**中暴露无遗。Moltbook 是一个专门为自主 AI Agent 设计的社交平台。为了追求开发速度，开发者完全依赖 AI 辅助的“情绪编程（vibe-coding）”工具进行构建，却漏掉了在其 Supabase 数据库上启用行级安全（Row Level Security, RLS）这一关键防御。

由于这一配置疏忽，公开的 API 密钥实际上沦为了管理级的万能钥匙。安全服务商 Wiz 的研究人员发现了这一漏洞，该漏洞导致多达 **150 万个 AI Agent 的 API 密钥**、私信及机密凭证被公开暴漏，甚至波及了包括安德烈·卡帕西（Andrej Karpathy）在内的行业大佬的 Agent 账户。这一事件给业界敲响了警钟：“情绪编程”如果脱离了诸如数据库访问策略等基础安全控制，将对整个 Agent 生态系统构成毁灭性的威胁。

#### 重构安全基石：构建面向 Agent 的新型安全架构
要在亚古尔给出的 20 个月窗口期内存活下来，企业必须转向**感知 Agent 的安全架构（Agent-Aware Security Architecture）**。这一技术蓝图主要由三大核心技术支柱构成：

1. **动态、短时效的范围标记（Dynamic, Short-Lived Scoped Tokens）**：弃用长效的 API 密钥或凭证，改用任务级、时间受限的 JWT（JSON Web Token），且其生存时间（TTL）必须极短。如果一个 Agent 的任务是修改某一条数据库记录，其令牌必须在几分钟内失效，且**仅**拥有对该特定行的写入权限。
2. **以工作负载为中心的 IAM 与密码学委托（Workload-Centric IAM & Cryptographic Delegation）**：Agent 必须被视作独立的“工作负载身份”，而非人类的虚拟替身。在多 Agent 协同链（例如运行在 LangGraph 上的系统）中，每次委托调用都必须携带密码学签名的证据链。这能确保随着任务在链条中流转，权限只能单向收敛（遵循最小特权原则），绝不可能被中途放大。
3. **可信数据环境（Trusted Data Environments, TDEs）**：Meta 率先推出了可信数据环境，用以沙箱化 Agent 的交互。TDE 允许 Agent 查询数据管道，但会对敏感字段自动进行脱敏屏蔽。此外，TDE 确保每一次输出都能追溯到其最原始的数据源，为人类运营者提供可被确定性审计的溯源链条。

#### 终局裁判：遗留系统能否涉险过关？
接下来的 20 个月，将决定哪些企业能够在 Agent 时代胜出，而哪些企业会在灾难性的系统瘫痪中被无情淘汰。以亚古尔佩戴的 Ray-Ban Meta 眼镜为代表的硬件设备已经就绪，AI Agent 本身也已整装待发，但它们身后的数据库与 IAM 安全层，却还没有做好准备。

随着科技博主们持续为 Moltbook 泄露事件的余波以及“情绪编程”的局限性争论不休，业界的共识已变得无比清晰：服务于人类节奏、基于人类信任的底层基础设施时代已经终结。能够在这场风暴中存活下来的组织，必然是那些不再将自主 Agent 仅仅视作简单的 API 工具，而是将其作为高权限、高流速、享有一等公民待遇的数字基础设施核心要素去对待的先驱者。
